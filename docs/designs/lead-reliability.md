# HBH lead reliability — local implementation contract

## Baseline and boundaries
Target: fix/egm-lead-reliability, origin jasonmanuel-cmd/HBH, baseline 8edeac030f2bb4600053145b881131d7f87f962c. Supabase remains default. The strict confirmed-row details save-before-alert fix is already present and must remain in the default path. Existing gaps are restart identity loss, stale/replayed details and crash between save and alert intent. Live deployment/config/recipients are unverified. No hosted operations, feature activation, packages, sends or copy edits are part of this work.

## Chosen contracts
Introduce a separate public reliability protocol, default OFF (`LEAD_RELIABILITY_ENABLED=true` explicitly enables); it does not use seller flags. Runtime requires a database readiness row in addition to the flag. Missing readiness rejects reliable requests without legacy fallback. Default-off routes retain existing behavior. Durable clients are identified by `reliability_version:1`; once activated, requests without it are rejected with retry/refresh instructions, never processed by both delivery paths. Activation requires all old server versions drained and cached pages refreshed. Old-version server routing must be disabled before enabling DB readiness; this is an operational prerequisite, not solved by a flag on one instance.

Public commands use random UUID `request_id` (initial inquiry uses submission_id) and random opaque UUID `recovery_key`; only these identifiers are stored persistently in browser localStorage, never contact data, payloads or signed tokens containing contact data. Treat recovery_key as a bearer capability; store its SHA256 on the server. Status requires both values; UUID alone is never authorization. Details also require the existing signed details token for execution; status cannot return another command's contact data. Initial status may reissue a details token only after matching the capability and committed command. No browser persistence of form contents. Storage failure blocks reliable submission before network. Pending identities survive logout/restart; absence/error does not clear them.

New `lead_commands`: request_id PK, owner_hash, kind (inquiry/details), lead_id, intent JSONB, state (committed/aborted), result JSONB, created_at. Durable execution and status/fencing serialize using the same transaction advisory lock on request_id. Execution validates immutable intent (normalized parsed payload, excluding generated consent_at), locks the lead, performs mutation and inserts command plus notification intents in one transaction. Concurrent identical retry returns original result; changed owner/kind/lead/intent returns conflict with no mutation. Completed replay never reads mutable lead fields to compare the original inquiry intent. An existing legacy lead ID with no command is a conflict, never silently adopted or re-alerted. No business deduplication by phone/email.

Status reports committed, aborted, or unresolved. A missing row is unresolved; status alone never grants a new identity. Explicit `fence` status operation takes the same lock and writes an aborted tombstone if missing. This waits for an executing transaction, so committed wins if execution committed, otherwise the tombstone rejects every late execution. A timeout is unresolved. Aborted is terminal and allows user-initiated fresh entry. No tombstone or intent deletion in this release. PostgreSQL atomic transactions make executing an uncommitted state; there is no durable promise of admission before commit. Lost response is resolved using status; same-ID retry with identical payload remains valid.

Details require UUID request_id, recovery key, signed lead reference and nonnegative `expected_revision`. New leads start `details_revision=0`. A before-update trigger increments details_revision whenever tracked details fields change, including HQ/legacy updates. Reliable update locks the row, checks expected_revision and only changes timeline/occupancy/condition_flags/desired_outcome. It returns exactly one matching lead ID and new revision; API requires that confirmation before success. A stale request produces a terminal aborted command, not an overwrite. Exact committed replay returns original result even after later edits. Deleted/spam/suppressed or foreign Standard-brand leads reject details. Existing token lifetime remains six hours; status can recover a committed outcome after token expiry with the capability, but cannot initiate a new details mutation.

## Atomic notification intent and external outcomes
New service-only `lead_alert_outbox`: UUID id, command_id FK, channel, target, payload snapshot, state pending/sending/accepted/uncertain/failed/suppressed, lease UUID, lease_until, attempts, provider_id, evidence, timestamps. Unique(command_id,channel,target). Initial intents preserve existing email recipients/defaults, webhook, staff SMS and separately consent-gated customer acknowledgement. Details preserve email/webhook only. Snapshot original content and routing; do not read current configuration to silently retarget a queued job. Secrets are never persisted. No new outreach or marketing. Customer SMS requires existing ACK flag, response consent and contact preference; recheck current consent/suppression before claim. Deleted/spam/suppressed records suppress jobs. No configured channels is a readiness failure in durable mode.

Separate manual worker `scripts/process-lead-alerts.mjs` with `LEAD_RELIABILITY_DISPATCH_ENABLED=true`; default OFF before any DB/network access. Production activation requires scheduled ownership, validated config, recipient review and monitoring, not merely this manual script. Claim uses row locks/SKIP LOCKED, one job, two-minute lease; expired sending becomes uncertain, never pending. Preflight credentials before claim; confirm at least 30 seconds remain before send. Each job is one external request (SMS recipient is one job). No automatic POST retry. Provider success with receipt => accepted (not inbox delivery); missing receipt, timeout, 5xx or malformed response => uncertain; explicit definitive 4xx rejection except 408 => failed. Webhook 2xx is acceptance evidence. Finish requires matching lease AND unexpired lease. Failure to finish leaves quarantine on expiry. Reconciliation is manual service-only RPC with evidence and explicit accepted/pending decision; no automatic resend of uncertain jobs. Exactly-once external delivery is NOT promised. Provider idempotency keys are supplementary only.

## Seller workflow recovery
Keep seller flags OFF and existing API auth/CSRF boundary. Add separate default-off `SELLER_COMMAND_RECOVERY_ENABLED` to permit rollout after schema. Existing seller command result rows remain authoritative. New `seller_command_recovery` records request_id, lead_id, prepared command, state admitted/aborted. A reliable execute wrapper takes the request lock, checks recovery identity and invokes existing seller_workflow in the same transaction; existing lead lock/revision/consent checks remain. Authenticated `ops-command-status` POST accepts request_id/id and optional fence. It returns committed with stored result, admitted with server-stored command if present, unresolved if absent; fence writes aborted tombstone under the same lock. A late execute cannot cross the fence. Cross-record lookup conflicts; unauthenticated HQ never reaches the handler. No trusting display name as a separate principal: HQ authorization is currently shared administrative access.

UI localStorage stores only request and lead UUIDs. After restart it checks status and offers fenced reconciliation for unresolved identity; it never re-enters an unknown event under a new ID. Same-page payload remains in memory for exact retry. On committed or aborted confirmation clear marker; 4xx alone does not clear it. Logout clears sensitive memory but retains opaque marker. If recovery flag is off, legacy behavior is unchanged and activation remains blocked until schema/client readiness. Recovering older memory-only commands after prior browser restart is not possible; no fabricated backfill.

## Release, operations and rollback
Local implementation is not activation approval. Apply additive schema only after backup/rehearsal and service-role grants/RLS validation. Deploy compatible server and clients with flags OFF; verify old paths. Drain old servers before enabling readiness and public capture/dispatcher together under an approved maintenance window. Ensure scheduler/operator assigned and no old sender still active. Do not backfill alerts for historical leads. Monitor oldest pending age (alert at five minutes), expired claims (immediate), uncertain/failed jobs (manual evidence review), unresolved commands and RPC errors. Stop admission on dispatcher outage rather than silently enabling legacy sends for durable commands. Existing queued jobs retain ownership during flag rollback; drain/reconcile before disabling worker. Never drop command/tombstone/outbox tables after writes, never replay all jobs. Roll back code only to a compatible version that recognizes durable markers; reverting to pre-protocol code after durable writes needs write freeze and explicit reconciliation. Physical schema removal only before first durable write and after proving no in-flight operations.

Alternatives: retaining legacy at-most-once attempts cannot close crash gap; enabling seller outbox changes behavior and risks disabled dispatch; client-only dedup cannot arbitrate concurrent writers. Selected separate transactional public command/outbox adds modest bounded storage and service-only SQL without provider migration. Risks: capabilities can be lost/cleared or stolen with XSS; no safe automatic recreation on lost storage, use staff reconciliation. Browser multi-tab storage requires serialization before minting IDs; use Web Locks for reliable form submission or block unsupported browsers. PGlite serial execution does not prove multi-connection PostgreSQL scheduling; SQL lock design plus hosted rehearsal required before activation. Retention/production schedule/owner and provider reconciliation evidence are deploy prerequisites, not assumed facts.

## Exact contracts — readiness review corrections
These decisions supersede any less specific wording above. All eight readiness findings are PROPOSE FIX, accepted under the user's existing authorization. No business decision blocks safe local implementation.

### Public transport and browser state
`GET /api/leads?reliability=1` returns no-store `{ok:true,enabled:boolean,version:1}` from application configuration only. Only this GET is added; other GETs retain 405. `POST kind:command_status` takes `{request_id,recovery_key,fence?:boolean}`. It works independently of capture/dispatch flags for already deployed schema; missing schema is 503/unresolved, never legacy fallback. Validate identifiers and size first, apply IP limiter to recovery (not phone limiter), before honeypot handling. No contact payload is returned except the authorized inquiry's short-lived details_token in a committed result. Status response is `{ok:true,state:'unresolved'|'aborted'|'committed',result?:{id,details_revision,details_token?,details_expired?}}`. Never return owner hashes/intent. Bad capability returns generic 403; malformed input 400; missing status 200 unresolved; RPC/network/malformed confirmation 503 unresolved. `fence:true` may create an aborted tombstone and is an explicit user recovery action. Committed replay is 200 even if readiness/capture is disabled; new reliable writes while disabled are 503, never legacy. Same-ID changed intent/owner/record is 409 (owner mismatch status remains generic 403). Stale details is 409 with state aborted, persisted transactionally. Only verified aborted/committed states release a pending command.

Reliable inquiry POST includes `{reliability_version:1,submission_id,recovery_key,...existingFormFields}`; details includes `{reliability_version:1,kind:'details',request_id,recovery_key,details_token,expected_revision,...detailsFields}`. All parsed immutable inquiry fields except id/consent_at are identity; details identity is parsed details plus expected_revision. Generated notification routing and timestamps do not participate in replay equality. Initial command result persists `{id,details_revision:0,details_expires_at:<epoch milliseconds>,phone,address}` server-side. API removes phone/address, signing a token with the ORIGINAL expiry only while unexpired. Status never extends expiry. Details tokens in reliable mode also carry the expected revision; client uses this revision, not a newer opportunistically refreshed revision, so HQ edits cause a visible stale/aborted outcome. There is no automatic retry applying old detail answers to a newer revision.

Public opaque localStorage keys: `hbh_reliable_inquiry` holds `{request_id,recovery_key}`, `hbh_reliable_details:<leadUUID>` holds `{request_id,recovery_key}`, `hbh_reliable_last` holds the committed inquiry's same opaque pair for thank-you recovery. No PII or token in these keys. Reliable path bypasses legacy hbh_lead sessionStorage completely. Keep committed inquiry marker through navigation/restart until explicit user start-new action; never mint a new ID merely on reload. Submit resolves an existing marker by status before any new write. Committed navigates to thank-you; unresolved allows same in-memory payload retry or explicit fence after restart; aborted permits user-initiated next submission. Corrupt/unreadable storage blocks, never replaces a marker. Web Lock `hbh-lead-command` encloses marker read/create, request/status and confirmed cleanup for all public forms; unsupported Web Locks block durable writes. Details uses recovered inquiry token in memory. UI messages/buttons use existing form status area; no layout redesign. Capability discovery errors do not choose legacy; they fail visibly. Off bootstrap with existing reliable marker still resolves it, never silently creates a legacy inquiry.

### SQL types, functions and ordering
Migration adds `details_revision integer NOT NULL DEFAULT 0 CHECK >=0`, with a BEFORE UPDATE trigger comparing `(timeline,occupancy,condition_flags,desired_outcome)` using IS DISTINCT FROM; on change set OLD.details_revision+1, otherwise preserve OLD revision to prevent arbitrary reset. Lead command table: `request_id uuid PK; owner_hash text NOT NULL CHECK 64 lowercase hex; kind text NULL CHECK inquiry/details; lead_id uuid NULL; intent jsonb NULL; state text NOT NULL CHECK committed/aborted; result jsonb NULL; created_at timestamptz NOT NULL DEFAULT now()`. No lead FK/cascade on commands/tombstones, so deletion cannot erase fencing evidence. Outbox command FK uses RESTRICT; `lead_id uuid NOT NULL` is retained for suppression lookup, not cascading deletion. Other fields described above are text/jsonb/uuid/timestamptz as named; payload JSONB NOT NULL, attempts integer default0, channel checked email/webhook/sms/customer_sms. Unique(command_id,channel,target); partial index created_at for pending and lease_until for sending. New tables enable RLS, revoke PUBLIC/anon/authenticated entirely, grant SELECT/INSERT/UPDATE to service_role; no DELETE. All functions SECURITY INVOKER SET search_path='', fully qualified tables, revoke EXECUTE from PUBLIC/anon/authenticated, grant only service_role.

`lead_reliability_control(singleton boolean PK CHECK singleton,enabled boolean NOT NULL DEFAULT false,worker_until timestamptz NULL)` starts disabled. `lead_worker_heartbeat()` sets worker_until=clock_timestamp()+interval '5 minutes' only; cannot enable capture. Worker calls only after preflight of configured channels. Production schedule must run more frequently than five minutes; admission SQL checks enabled AND worker_until>clock_timestamp(), preventing new writes during worker outage. Existing committed replay/status/fence and draining remain available. Runtime LEAD_RELIABILITY_ENABLED plus readiness is required for new writes; seller operations flag TRUE is incompatible with this public path until separately reviewed (503), avoiding competing queues.

RPCs: `lead_command_status(request_id uuid,owner_hash text,fence boolean DEFAULT false) returns jsonb`; `lead_command_execute(request_id uuid,owner_hash text,kind text,lead_id uuid,intent jsonb,alerts jsonb,allow_new boolean) returns jsonb`; `lead_claim_alert() returns setof lead_alert_outbox`; `lead_finish_alert(job_id uuid,lease uuid,state text,provider_id text) returns boolean`; `lead_reconcile_alert(job_id uuid,decision text,evidence text) returns boolean`; `lead_worker_heartbeat() returns boolean`. Execute checks existing command under advisory transaction lock FIRST; validates owner/kind/lead/intent, returns original terminal result before readiness. Then readiness and row lock; writes aborted result for stale/ineligible details without throwing; mutation, command and alerts commit together. inquiry row construction uses explicit normalized fields via jsonb_populate_record plus schema defaults (never accept staff fields from public). Error result `{state:'aborted',code:'STALE'|'INELIGIBLE'}` persists and returns; conflict raises 23505 and rolls back. Status takes same advisory lock; matching existing row returns state/result, absent without fence unresolved, absent with fence inserts null-intent tombstone. Prefix public and seller advisory namespaces separately. Lock ordering: command advisory then lead row then outbox insertion. Outbox claim locks one pending job then lead; suppression edits are checked under that row lock at admission; suppression after claim cannot revoke an already admitted external call and is explicitly an in-flight limit.

### Delivery snapshots and readiness
Email is ONE job per original recipient array, preserving envelope/subject/body/reply-to. Target is canonical JSON of recipient array, payload contains complete email body, no API key. SMS/customer_sms ONE job per E.164 recipient; payload `{to,from,body}`. Webhook target is SHA256 of configured full URL; payload contains only original event body. Dispatcher requires current URL hash to match, otherwise leaves job pending and reports configuration mismatch before external I/O; never persists secret-bearing URL or silently retargets. Credential rotations for unchanged routing are allowed; routing changes require explicit reconciliation. Claim accepts only jobs whose channel configuration was preflighted? Selected contract instead claims one job, validates its snapshot before send, and on configuration mismatch safely releases to pending using matching unexpired lease with a dedicated `lead_release_alert(job_id uuid,lease uuid)` RPC; this release is allowed only before invoking external fetch. No send ambiguity can use release. A missing provider receipt is uncertain; webhook 2xx records `http:<status>`; Resend id and Twilio sid are accepted evidence. All POST attempts use fetch directly with ten-second timeout and no retry.

### Seller simplification and browser lifecycle
Remove the proposed admitted state: preparation and execution are one atomic transaction. No separate durable admission is claimed. `seller_command_recovery(request_id uuid PK,lead_id uuid NOT NULL,state text CHECK aborted,created_at timestamptz default now())` is a fencing tombstone table. `seller_command_status(request_id uuid,lead_id uuid,fence boolean) returns jsonb` serializes with execution, checks seller_commands first, returns committed result on matching lead, otherwise aborted tombstone or unresolved, and fences missing identity if explicitly requested. `seller_workflow_reliable(command jsonb,actor_name text) returns jsonb` locks same request namespace, returns existing matching fingerprint result BEFORE mutable prerequisites, rejects tombstone, then invokes existing seller_workflow. No prepared payload persists outside the existing seller_commands snapshot. Unknown errors and any 4xx preserve pending identity until status/fence confirms outcome. Existing seller flag plus recovery flag required for new reliable execution; status/fencing stays reachable to authenticated HQ even when operations/recovery flags roll back. Existing legacy workflow endpoint refuses missing reliability_version when recovery is enabled; drained old servers are a prerequisite.

HQ storage key `hbh_seller_pending` contains only `{request_id,id}`. Lock `hbh-seller-command` encloses marker creation/status/fence/execute. Overview exposes recoveryEnabled. On load/restart, marker causes locked controls and authenticated status; committed or aborted clears marker only after confirmed response, unresolved displays a dedicated resolve-original button (fence) rather than inventing an event. Same-page retry retains exact in-memory body. Logout removes body/data but not marker. Cross-tab existing marker is read INSIDE lock and resolved before new command creation. If storage fails, do not submit.

### Design-review correction: deletion-proof seller outcome evidence
seller_command_recovery additionally permits committed state and stores fingerprint text plus minimal result JSONB `{id,ops_revision}`. No lead FK/cascade. Migration copies existing seller_commands terminal identity/fingerprint/minimal result into it; no notifications generated. Reliable wrapper writes committed recovery evidence in the SAME transaction as seller_workflow. Terminal tombstones have null fingerprint/result. This supersedes the tombstone-only definition above.

## Final-review resolutions and operational clarifications
Seller request locks canonicalize request IDs through uuid before hashing. The outcome-preservation trigger also takes that lock and rejects any conflicting aborted/committed evidence, rolling back the entire workflow even for a legacy RPC caller. API and browser require matching result ID and nonnegative integer ops_revision before acknowledging or releasing identity. Same-page 4xx preserves the pending reference and exposes explicit fenced resolution.

Configuration release now means pre-send FAILED quarantine with evidence `Configuration unavailable before external call`, not pending. It clears worker_until; heartbeat refuses to renew admission health while any such job is failed. Other pending jobs can still drain. After restoring the exact routing configuration, service-only reconciliation with evidence may move the quarantined job to pending; the next valid heartbeat permits admission. This prevents one removed webhook configuration from starving unrelated email/SMS or advertising false readiness. No uncertain send uses this release operation.

Browser marker writes/removals notify bound controls immediately, including delayed bootstrap failure paths. A separate explicit Start another inquiry action verifies terminal status before clearing the old inquiry marker; mere reload/error never does so. Existing unresolved legacy session references block new durable identities during activation and require staff reconciliation rather than unsafe adoption. Confirmed new reliable submissions retain existing conversion analytics; replay/status recovery is not counted as a fresh conversion. The additional shared browser script is static/command-recovery.js, loaded by src/templates.mjs and static/hq/index.html; these are script inclusions only, not a page redesign.

SQLSTATE mapping: public known identity/serialization conflicts return409, capability mismatch403, validation400/401, unknown/readiness/malformed result503 with unresolved identity retained. Seller preserves existing40001 or transport400 ->409 and explicitly maps23505 ->409 (including the unshipped adapter's preserved uniqueness code); unknown or malformed confirmation502. Browser does not release identity based on any HTTP error alone. Neon correction is a separate local patch artifact against92c4a3d97c3947abf5e0d482a98a94aecedc4b28, no installed runtime binding.
