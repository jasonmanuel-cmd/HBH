# Seller operations development handoff

This is a local implementation draft extending HBH's existing HQ, not a production rollout. Harbison Standard's authenticated bridge contract is unchanged. No production credentials were read or changed, no remote migration was applied, no branch was pushed, and no real records or external communications were used.

## Run locally

Use Node 22+ and `npm ci`, then `npm run dev -- --mock`. The server binds to loopback by default. HQ login is `demo`; the synthetic reviewer password is `review-demo`. These are hardcoded development fixtures, not production credentials. The mock replaces every server-side fetch: only its local database adapter is accepted; all other URLs throw. Data lives in memory and disappears when the process stops. No .env file is loaded. Do not use preview deployments as a test database: their configured services may be production.

`npm test` runs existing regression tests and a PostgreSQL-backed synthetic workflow. `npm run build` builds the unchanged public design plus the HQ extension. No separate lint or TypeScript script exists; all changed JavaScript modules are syntax-checked with `node --check`.

## What was built

- `/hq/operations` extends the existing HQ shell. Jay/Billy triage, next follow-up, and Nathanael handoff reuse the lead table. The existing lead drawer links to the inquiry workbench and makes evidence-controlled workflow fields read-only when enabled.
- Research records never enter `leads`. Supported CSV/JSON fields are `source_system`, `source_record_id`, `source_url`, `source_date` (YYYY-MM-DD), `jurisdiction`, `apn`, `address`, `assertions`, and `conflicts`. CSV assertion/conflict cells can contain JSON arrays or a single string. Unknown facts remain null; every new revision starts HOLD. No contact details, scores, messages, scraper calls or audience uploads are generated.
- Source system + source record ID identify history; normalized content identifies a revision. Exact repeats do nothing. New revisions preserve earlier evidence and invalidate earlier verified state. Overlong source IDs/provenance fail validation instead of being truncated. Name-only matching is not implemented.
- Imports require a separately authorized reviewer, a signed 15-minute preview of the exact normalized payload, and explicit commit. The import and audit entry are transactional. A repeat after an uncertain response is safe.
- Reviews require evidence, revision matching and an ownership/mailing/title/representation confirmation. Conflicted or incomplete parcel facts cannot become verified. Linking requires reviewer permission, an existing unsuppressed inquiry with response permission, matching normalized property addresses, explicit requester identity confirmation and evidence. Matching is deliberately conservative: formatting differences beyond punctuation/case must be resolved in the inquiry before linking. No research promotion endpoint exists.
- Contact attempts record channel, actual result, evidence and operator label. Failed attempts do not create response timestamps. Qualification requires a recorded conversation, authority, service fit, timeline and next step. Handoff assigns Nathanael. Appointments, kept/no-show/cancelled results, outcomes and opt-out are explicit events. Advanced stages are preserved when logging activity. Reopening a closed inquiry explicitly clears its current closure/qualification/handoff state, retaining the event history.
- Response permission is separate from marketing. Standard's existing bridge records response consent as unknown/false; an operator must document actual permission before using the contact workflow. Suppression cannot be cleared through this workbench. It is never used to disguise research records.
- Source metrics are current-record snapshots, not an immutable historical conversion funnel: reopening can reduce current qualification/outcome counts. They use inquiry data only; historical imports are excluded. New response statistics use explicit recorded contact evidence, never a stage change. The recorded-at timestamp is used, so delayed activity entry can overstate response time. Research source/revision/hold counts are separate. Existing historic qualification/first-contact timestamps are not invented or backfilled.

## Access model and limits

The existing HQ shared password still grants broad CRM read access and ordinary operator capabilities. A display name is self-asserted: audit labels do **not** prove an individual identity. A separate `HQ_REVIEW_PASSWORD` adds a reviewer capability to imports, reviews, links and reconciliation. It is kept in the current page only, cleared on logout/reload, compared server-side and throttled for failed attempts. The throttle is in-process, not a distributed account lockout. This is not individual RBAC or MFA; do not represent it as such. Before broader staff access or sensitive real-data ingestion, review whether named authenticated identities are required. No production reviewer credential was created.

New tables have RLS enabled with no browser-role policies; all privileges are revoked from PUBLIC, anon and authenticated. Only the server service role may access them. RPCs use SECURITY INVOKER with a pinned empty search_path; EXECUTE is revoked from browser roles. The service-role key never enters the browser. RPC request validation and operator attribution happen in the authenticated HQ API. The service-role credential remains a highly privileged trust boundary.

The workbench currently displays the latest 500 rows per queue and up to 1,000 recent audit entries, with visible limitation notices. Metrics describe that window, not lifetime totals. There is no full-history paging UI yet. Records and audit history remain in the database. Existing links retain historical meaning if a new source revision arrives; renewed verification is required before a new link. Administrative record purge can remove an inquiry and its linked outbox/command rows; research audit entries are retained. Review retention policy before real research import.

## Notification behavior

`SELLER_OPERATIONS_ENABLED=true` writes `notification_mode=durable`. The database inserts an internal notification job in the same transaction as a new inquiry, including Standard bridge inquiries and manually entered inquiries. Research and historical imports never enqueue jobs. Duplicate inquiry IDs do not add jobs. Missing schema in this mode fails storage explicitly; the legacy schema fallback is disabled so it cannot falsely report a queued notification.

`SELLER_OUTBOX_DISPATCH_ENABLED` defaults OFF. The only worker is the manually invoked `node scripts/process-outbox.mjs`; no cron, public dispatch endpoint or recurring job was created. With dispatch off the script performs no database or provider access. In durable mode the old inline email/webhook/SMS path is bypassed. Only the internal email adapter is implemented for the future worker. Homeowner messaging, marketing, missed-call handling, Telnyx and availability monitoring remain disabled/deferred.

The worker claims one pending job with a two-minute lease and refuses provider I/O if fewer than 30 seconds remain. Provider requests have a ten-second timeout and use a stable job idempotency key. A provider receipt becomes `accepted`, which is **not inbox delivery**. Known rejections become `failed`; missing receipts or ambiguous failures become `uncertain`. A stale worker cannot confirm a reclaimed lease. Expired claims are quarantined on the next worker invocation, not automatically resent. Recovery requires reviewer-authenticated provider evidence: confirm acceptance, or confirm non-acceptance before returning the job to pending. Until a worker is approved/running, elapsed sending leases do not change state by themselves.

Exactly-once email delivery is not claimed. A process can pause between checking a lease and making the network request, and provider idempotency guarantees have a finite vendor-defined window. Before retrying an uncertain job, reconcile the original provider request and ensure no stale worker remains active. Provider acceptance/receipt loss, network failures and actual inbox receipt must be validated in a controlled staging/activation test.

## Migration and activation order

No steps below have been executed remotely.

1. Review the local diff and isolate a nonproduction Supabase/PostgREST target with synthetic data and no live provider credentials. Confirm its schema history and backups. Keep both flags false; leave all existing production recipients/configuration untouched.
2. For a fresh database, apply `supabase/schema.sql`, then migrations `002_family_transition.sql`, `003_options_form.sql`, `004_harden_trigger_functions.sql`, corrected `005_crm_improvements.sql` / `006_lead_trash.sql` in that numerical order, then `20261031235109_seller_operations.sql`. File 005 itself is unchanged. File 006 now preserves the extra view columns from 005; previously the clean sequence failed with "cannot drop columns from view".
3. For an existing database already through 006, verify the actual columns/triggers/views and apply **only the new migration** after review. Do not replay the base schema or blindly rerun historical migrations. The new migration reconciles the known v_uncontacted variants, including opt-out and trash filters. It is transactional and intentionally not a rerunnable script. Never apply it twice; use recorded migration history.
4. Deploy the reviewed application with both flags false first. Verify legacy intake and HQ behavior against the isolated target. Then enable `SELLER_OPERATIONS_ENABLED=true` in that isolated environment and provision its separate reviewer capability through an approved secret workflow. Test synthetic public intake, Standard bridge, duplicate retries, review/link workflow, access denials and migration failure behavior.
5. Keep dispatch false. Inspect the pending queue and failure/reconciliation UI. Validate role grants and schema cache through actual PostgREST and run actual multi-connection PostgreSQL contention tests. PGlite is not sufficient for these deployment gates.
6. Production migration/deploy and any real-data import require separate approval. A later controlled internal notification test requires explicit dispatch approval and a designated runner. Confirm the existing recipient configuration remains Jay and Billy; do not replace it with defaults. Confirm actual receipt independently. No external dispatch should be enabled merely to make a preview look functional.

Application flags off, migration absent: the public forms, bridge and legacy HQ remain compatible with the existing schema; all original tests cover that path. Flags off, migration present: new legacy inquiries still use legacy notification behavior, the existing nathanael assignment default and legacy contact-stamping behavior. Durable jobs are only created for explicitly opted-in rows. Previously opted-in records keep evidence-based status semantics even after the application flag is turned off. The new migration fixes the existing uncontacted view's suppression/trash filtering and adds tables/columns; it does not retroactively notify or reassign existing records.

## Rollback

First disable `SELLER_OUTBOX_DISPATCH_ENABLED` and stop the separately approved worker, if one exists. Reconcile any in-flight/uncertain jobs before permitting another worker. Then disable `SELLER_OPERATIONS_ENABLED` or redeploy the last reviewed application commit. Keep the additive tables and audit history: do not drop them as an emergency rollback. Legacy intake resumes for new rows; queued durable jobs remain retained and must not be blindly drained after a rollback. Existing durable inquiries preserve their evidence timestamps and assignments. If restoring pre-migration status-trigger semantics or removing schema objects is required, prepare a separate reviewed database rollback after backup; no destructive rollback is bundled.

## Verification boundary

PGlite runs actual PostgreSQL SQL/PLpgSQL, constraints, triggers, functions and role grant denials in memory. The test harness applies the entire migration sequence and drives the real HQ/public/bridge handlers through a small local PostgREST-shaped adapter. It proves atomic changes and command replay behavior in this harness. Browser checks use the same SQL-backed synthetic mock.

It does not run the Supabase platform, Supabase Auth, production grants/default privileges, actual PostgREST serialization/schema cache, or independent concurrent PostgreSQL connections. Promise.all claims on one PGlite instance are queued on its single connection: they prove distinct sequential claims, not real SKIP LOCKED contention. Docker's local engine was unavailable. Production/staging PostgREST, Supabase advisors, true concurrent workers, Resend's current idempotency semantics and actual inbox delivery remain unrun. No independent lint/type-check script exists.

Independent read-only review covered authorization, research separation, SQL/RLS and outbox recovery. It found the batch-lease expiry risk, truncating source identifiers and accidental reopening by activity logging; each was fixed with regressions. The reviewer also identified a lost-response replay edge on reopen; prior command fingerprints are now checked before current-state prerequisites, with a committed-reopen replay test. No critical auth/RLS bypass was found in that review. This does not constitute a production security certification.

## Scenario coverage

- Existing public intake, duplicate/retry safety, sanitized errors, bridge authentication, CRM trash/export, identity, metadata, consent copy, analytics and public design regressions.
- Anonymous access rejected for all new actions; shared HQ without reviewer capability cannot import/reconcile; browser DB roles denied new-table access and RPC execution; simulated service-role RPC access succeeds.
- Invalid/bounded CSV/JSON, invalid URLs/dates, overlength identities, exact repeat versus changed source revision, expired/tampered preview, atomic import audit and no added inquiry/outbox rows.
- Stale review, unverified research, unrelated address, unchecked requester identity and suppressed inquiry links denied; supported human-approved link succeeds.
- Contact evidence, permission provenance, failure results, prerequisite qualification/handoff, booked/kept appointments, outcomes, suppression, replayed request IDs and explicit reopen semantics.
- Research/historical separation in metrics; legacy flags-off behavior before and after schema additions; durable-mode missing migration fails closed.
- Dispatch-off no-I/O, distinct claims, expired lease quarantine, lost lease acknowledgement, known rejection versus uncertain receipt, reviewer reconciliation and mocked accepted receipt.

See `docs/evidence/test-results.txt`, `build-results.txt` and browser evidence for final verification output. The smallest next gated step is approval for an isolated Supabase/PostgREST validation target using synthetic records with external dispatch still off. Publication of a draft PR is a separate explicit push decision because repository integrations may create previews.

Overlapping identical workflow requests may briefly conflict if the first commits between the second request's replay lookup and state validation. A subsequent exact retry returns the stored result without duplicate activity. Validate this timing with independent PostgreSQL connections in staging.
